# Presentation Guide — Final Project Documentation v1.0

ระยะเวลาแนะนำ 12–15 นาที เตรียม Browser และสารบัญเอกสาร เปิดบัญชีทดสอบแต่ละบทบาทไว้ใน session แยก และใช้ข้อมูลสมมติในฐานข้อมูลทดสอบสำหรับธุรกรรม ห้ามแสดงรหัสผ่าน token หรือข้อมูลลูกค้าจริงบนจอ

| เวลา | ลำดับนำเสนอ | บทพูดแนะนำ |
|---|---|---|
| 0–2 นาที | ภาพรวมและหน้าเว็บ | “โครงงานนี้เชื่อมผู้ซื้อ ผู้ขาย และผู้ดูแลระบบ โดยเน้นความถูกต้องของคำสั่งซื้อและการแยกสิทธิ์” |
| 2–4 นาที | Architecture และ ER | “หน้าเว็บใช้ Next.js ติดต่อ Laravel ข้อมูลหลักอยู่ใน PostgreSQL รายการคำสั่งซื้อเก็บชื่อและราคาขณะซื้อเพื่อรักษาประวัติ” |
| 4–7 นาที | Buyer เลือกสินค้า ตะกร้า Checkout และประวัติ | “Backend ตรวจราคาและสต็อกใหม่ทุกครั้ง การส่งคำขอเดิมซ้ำไม่สร้างคำสั่งซื้อซ้ำ สถานะเริ่มต้นยังรอชำระ” |
| 7–9 นาที | Seller สินค้าและคำสั่งซื้อ | “ผู้ขายจัดการได้เฉพาะสินค้าตนเอง การลบเป็น archive ประวัติคำสั่งซื้อยังอยู่” |
| 9–11 นาที | Admin และรายงาน | “Admin ตรวจรับเงินก่อนเปลี่ยนเป็น paid จากนั้นจึงจัดส่งและสำเร็จ รายงานนับเฉพาะยอดชำระที่ตรงกับคำสั่งซื้อ” |
| 11–13 นาที | Wishlist และรีวิว | “รีวิวต้องมาจากการซื้อสำเร็จและผ่านการอนุมัติ คะแนนเฉลี่ยจึงอิงข้อมูลที่ผ่านเงื่อนไข” |
| 13–15 นาที | Testing, CI/CD และข้อจำกัด | “เราแยกผลตรวจซอร์สโค้ด ผลทดสอบเดิม และผล Browser ปัจจุบันอย่างชัดเจน ระบบยังไม่มี payment gateway และการคืนเงินอัตโนมัติ” |

ถ้าเข้า Buyer/Seller/Admin ไม่ได้ ให้ใช้ ER และอธิบายคู่มือจากโค้ด พร้อมกล่าวว่า “หน้านี้ยังไม่ได้ยืนยันผ่านบัญชีบน Production ในรอบนี้” ไม่ใช้ภาพเก่าประกอบโดยอ้างว่าเป็นผลสด ไม่ยืนยันชำระเงินปลอมหรือสร้างคำสั่งซื้อบนร้านจริงเพื่อการนำเสนอ

คำถามที่ควรเตรียม: เหตุใด role guard ต้องอยู่ Backend, idempotency ต่างจากการปิดปุ่มอย่างไร, เหตุใด archive จึงรักษาประวัติได้, pending ต่างจาก paid อย่างไร และเหตุใดเว็บตอบ 200 จึงไม่ยืนยันว่า deploy ใช้ SHA ล่าสุด

## เตรียม Demo และตรวจสิทธิ์

เตรียม Buyer A/B และ Seller A/B ในฐานข้อมูลทดสอบแยก เพื่อแสดงว่าบัญชีอื่นอ่านคำสั่งซื้อหรือแก้สินค้าที่ไม่ใช่ของตนไม่ได้ ทดลอง refresh หน้ายืนยันแล้วตรวจว่าไม่มีคำสั่งซื้อซ้ำ และทดลองยกเลิก pending แล้วตรวจว่าคืนสต็อกครั้งเดียว ผู้เปลี่ยนสถานะคำสั่งซื้อคือ Admin

Browser fixtures อยู่ที่ `backend/tests/browser-fixtures.php` ต้องใช้ APP_ENV=testing และฐานข้อมูลทดสอบหลัง migrations เท่านั้น ห้ามใช้ migrate:fresh กับข้อมูลเดิม ห้ามรันชุด RefreshDatabase พร้อม Browser suites เพราะอาจล้างข้อมูลระหว่าง Demo ต้องมี Playwright/Chromium; หากไม่ได้ติดตั้งในโครงการให้ตั้ง PLAYWRIGHT_MODULE ตามเครื่อง ห้ามนำผลที่ยังไม่ได้รันมาอ้างว่าผ่าน
